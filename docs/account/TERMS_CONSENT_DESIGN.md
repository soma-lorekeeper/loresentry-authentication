# Auth 약관 동의 설계

> **책임:** 약관 버전·동의 기록, 가입 대기·완료·실패 처리와 동의 화면의 입력 규칙을 정한다.
>
> **확인할 때:** Google 인증 후 동의를 받거나 재동의·동의 저장을 구현할 때.
>
> **관련 기준:** 약관 전문은 [서비스 이용약관](../privacy/TERMS_OF_SERVICE.md), 개인정보 안내는 [처리방침](../privacy/PRIVACY_POLICY.md)을 본다.

Auth가 약관 원문·버전과 사용자별 동의 기록을 관리한다. Google 인증 후 필요한 동의가
확인되어야 가입을 완료하고 서비스 로그인 세션을 발급한다.

목표 설계이며 약관 테이블·가입 대기·동의 완료 API는 미구현이다.
기존 계정 항목은 [계정 ERD](AUTH_ERD.md), 인증 절차는 [로그인 흐름](../login/LOGIN_FLOW.md),
세션 발급은 [세션 계약](../session/SESSION_DESIGN.md)을 따른다.

초기 동의 대상은 [서비스 이용약관](../privacy/TERMS_OF_SERVICE.md)이다.
[개인정보 처리방침](../privacy/PRIVACY_POLICY.md)은 조회 링크로 제공하며 일괄 동의 항목으로 합치지 않는다.
원고·외부 AI·보유기간 등 서비스 정책은 두 공개 문서 초안에서 관리한다.

## 1. 약관 원문과 동의 기록

초기에는 Auth PostgreSQL에 아래 두 테이블을 추가하는 설계를 권장한다.

| 테이블 | 컬럼 | 제약·역할 |
|---|---|---|
| `terms_versions` | `id uuid` | PK |
| | `terms_type varchar`, `version varchar` | NOT NULL, 두 컬럼 조합 UNIQUE. 초기 동의 대상은 `SERVICE_TERMS` |
| | `title text`, `content text` | NOT NULL. 화면에 제공한 제목과 전문 |
| | `published_at timestamptz`, `effective_at timestamptz` | NOT NULL. 공개·시행 시각 |
| `user_terms_acceptances` | `user_id uuid` | FK → `users.id` |
| | `terms_version_id uuid` | FK → `terms_versions.id` |
| | `accepted_at timestamptz` | NOT NULL. 서버가 동의를 접수한 시각 |

`user_terms_acceptances`의 PK는 `(user_id, terms_version_id)`다. 동일 동의의 재요청은
기존 시각을 유지한다. 공개된 약관 본문은 수정하지 않고 변경마다 새 버전을 추가한다.
동의 기록에 원문을 복제하거나 `users`의 boolean 하나로 동의 내용을 대체하지 않는다.

새 버전 등록 자체가 기존 회원의 재동의 의무를 만들지는 않는다. 신규 가입에 적용할 버전과
기존 회원에게 재동의가 필요한 버전·적용일은 운영 정책으로 명시한다. 문서의 수정 순서만으로
모든 기존 회원을 차단하지 않는다. 기록이 참조하는 원문은 동의 기록의 보유기간 동안 유지한다.

이 구조는 서비스 이용약관 수락 이력용이다. 향후 철회 가능한 선택적 개인정보 동의를
추가한다면 동의·철회 이벤트와 현재 상태를 별도로 설계한다.

## 2. Google 인증 이후의 가입·동의 흐름

1. `prepare`는 기존 OAuth 준비만 수행한다. 약관 동의 ID는 이 단계에서 요구하지 않는다.
2. 콜백에서 OAuth 임시 상태를 소비하고 Google 신원을 검증한다.
3. `(provider, provider_id)`로 기존 회원과 적용 대상 약관의 동의 기록을 확인한다.
4. 필요한 동의가 있는 기존 회원은 기존 로그인 흐름으로 세션을 발급한다.
5. 신규 회원 또는 필요한 동의가 없는 회원은 `TERMS_REQUIRED` 분기로 보낸다.
   신규 계정과 새 서비스 세션은 아직 생성하지 않는다. 검증된 신원을 가입·동의 대기 상태로 보관한다.
6. BFF는 가입 대기 식별자를 HttpOnly 쿠키로 설정하고 고정된 프론트 약관 화면으로 이동시킨다.
7. 약관 화면은 별도 조회 API로 대상 버전 ID·제목·전문을 받는다. 약관 전문을 OAuth 콜백에 넣지 않는다.
8. 사용자가 동의하면 별도 완료 API에 동의한 버전 ID를 제출한다. 구글 콜백을 다시 호출하지 않는다.
9. Auth는 대기 상태와 대상 버전을 검증한다. 신규 회원이면 계정·Google 연결·동의 기록을
   같은 PostgreSQL 트랜잭션으로 저장한다. 기존 회원이면 동의 기록만 추가한다.
10. DB 커밋 후 세션 저장 성공을 확인해 로그인 쿠키를 발급하고 가입 대기 상태와 쿠키를 정리한다.

`POST /auth/signup/complete`는 논의 중 사용한 경로 예시다. 기존 회원의 재동의도 처리하므로
최종 API 이름·상태 코드·응답 DTO는 구현 전에 Auth·BFF 계약에 반영한다.
`TERMS_REQUIRED`는 Google 인증 실패와 구분되는 정상적인 추가 절차 상태다.
이 분기에서도 OAuth 요청은 이미 소비되었으므로 BFF가 기존 OAuth 임시 쿠키를 정리하고
별도의 가입 대기 쿠키를 설정한다. Google 코드나 소비된 OAuth 상태를 재사용하지 않는다.

브라우저 JavaScript는 가입 대기 식별자 원문을 읽거나 본문에 넣지 않는다. 쿠키를 포함한 요청을
BFF에 보내면 BFF가 내부 Auth 요청에 식별자를 전달한다. 본문에는 사용자가 동의한 버전 ID만 넣는다.
조회 때 보여준 버전을 대기 상태에 연결하고, 완료 시 일치 여부를 확인한다. 그 버전을 더 이상
허용할 수 없다면 새 내용을 보여주고 다시 동의받으며, 다른 버전으로 자동 치환하지 않는다.

## 3. 가입 대기 수명과 실패 처리

가입 대기는 Google 인증 성공 후 생성 시점부터 **30분의 절대 만료**를 초기값으로 한다.
약관 조회나 새로고침으로 연장하지 않는다. 기존 OAuth 요청의 5분 만료와 별개다.

가입 대기 식별자는 예측 불가능한 난수로 발급하고 서버에는 해시로 조회하도록 설계한다.
BFF의 운영 쿠키는 HttpOnly·Secure·Path=/·Domain 없음·SameSite=Strict와 남은 유효기간에
맞춘 Max-Age를 사용한다. 로그인 세션과 쿠키 이름·권한·저장소를 구분하며 URL·로그·브라우저
저장소에 원문을 넣지 않는다. 완료·취소 요청에는 BFF의 Origin·CSRF 검증을 적용한다.

| 상황 | 처리 |
|---|---|
| 창을 닫고 만료 전에 같은 브라우저로 복귀 | 쿠키와 서버 상태가 남아 있으면 약관 화면을 이어서 표시 |
| 쿠키 삭제·가입 대기 만료 | Google 로그인부터 다시 시작 |
| 미동의·이탈 | 신규 계정·동의 기록·서비스 세션을 만들지 않고 만료로 임시 정보 정리 |
| 명시적 취소 | 가입 대기 상태와 쿠키를 정리 |
| 신규 가입의 DB 저장 실패 | 계정·Google 연결·동의 기록 전체 롤백 |
| DB 커밋 후 세션 저장 실패·결과 불명 | 계정·동의 기록은 유지하고 로그인 재시작으로 복구 |

가입 대기 30분 동안에는 이름·이메일 등 검증된 Google 정보가 임시로 처리된다.
따라서 “약관 동의 전에는 개인정보를 전혀 처리하지 않는다”고 안내하지 않는다.
이 임시 처리는 사용자가 요청한 가입 절차 진행 목적에 한정한다.

동시 완료 요청은 하나만 처리 권한을 얻도록 원자적으로 제어한다. PostgreSQL과 Redis를
하나의 트랜잭션처럼 취급하지 않는다. 처리 권한을 소비한 뒤 실패하거나 결과가 불명확하면
같은 요청으로 세션을 반복 발급하지 않고 로그인 재시작으로 복구하는 방향을 기본으로 한다.
동시 가입 충돌은 기존 `(provider, provider_id)` 고유 제약으로 막고 승리한 계정을 조회한다.

기존 회원의 재동의 거부는 계정 삭제를 의미하지 않는다. 이미 발급된 세션의 처리와 기능 제한은
개정별 적용 정책을 정해야 하며, 로그인 시점 확인만으로 모든 기존 세션이 차단된다고 간주하지 않는다.

## 4. 구현 전 확정할 사항

- 약관 조회·동의 완료 API의 경로, 상태 코드와 응답 DTO.
- 신규 가입 대상 버전과 기존 회원 재동의 적용 시점·기능 제한·기존 세션 처리.
- 탈퇴 시 동의 기록 삭제 여부·시점. 별도 보유가 필요하면 근거와 기간을 먼저 정하고 처리방침에 반영한다.

## 5. 가입 화면 문구와 동의 입력

아래 문구를 가입 화면에서 [이용약관 전문](../privacy/TERMS_OF_SERVICE.md)과 연결해 사용한다.
체크박스는 기본적으로 선택되지 않은 상태로 표시하고, 사용자가 실제로 선택한 버전만 제출한다.

> **[필수] Lore Sentry 서비스 이용약관에 동의합니다.**
>
> 원고는 에디터의 저장·편집·분석 기능 제공을 위해 처리되며, 분석에 외부 AI가 사용될 수 있습니다.
> 원고의 권리는 해당 권리자에게 유지되고, 다른 사용자에게 공개되지 않습니다.
>
> 서비스 이용약관 전문 보기 · 개인정보 처리방침 보기
>
> 약관에 동의하지 않으면 가입을 완료할 수 없습니다.

버튼 문구는 **“동의하고 가입 완료”**로 한다. 기존 회원의 재동의 화면에서는 **“동의하고 계속”**으로 구분한다.
개인정보 처리방침은 조회 링크로 제공하며, 이 문구에 개인정보 동의 항목을 포괄적으로 합치지 않는다.
표시할 실제 문서 버전 ID와 원문은 [약관 저장 규칙](#1-약관-원문과-동의-기록)을 따른다.

작성 기준: [약관법 제3조의 명시·설명 의무](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029708921).

검증 시나리오는 [테스트 계획](../implementation/TEST_PLAN.md#약관-동의)을 따른다.
