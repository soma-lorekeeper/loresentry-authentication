# 사용자별 단일 로그인 세션 설계

**사용자마다 Redis 레코드 하나로 활성 로그인 세션과 현재 RT를 관리한다.**
새 로그인은 기존 세션을 교체한다. BFF는 AT 검증 후 활성 세션을 조회하고,
Auth는 로그인·재발급·로그아웃에 따른 상태 변경을 전담한다.

- 작성일: 2026-09-24.
- 상태: Auth 구현·Redis 7.4 및 Valkey 9.0.6 테스트 완료. BFF·프론트·운영 반영은 후속 작업.
- 검증과 전환 인계: [SESSION_HANDOFF.md](../../../docs/auth/implementation/SESSION_HANDOFF.md).
- 독자: Auth·BFF 구현 담당자와 프론트·인프라 연동 담당자.

이 변경을 구현할 때는 이 문서의 단일 로그인, JWT `sid`, 상태 저장·갱신·폐기,
BFF 조회 및 오류 계약을 기존 문서보다 우선한다. 기존 문서의 다중 로그인 허용,
RT별 `GETDEL`, BFF의 Redis 미조회 규칙은 이 범위에서 대체된다.
OAuth 신원 검증·계정 저장·서명키·쿠키·CSRF·CORS의 나머지 계약은 유지한다.

## 1. 목표와 적용 범위

새 로그인의 Redis 저장이 완료되면 이전 세션의 AT와 RT를 다음 인증 검사부터 거절한다.
정상 재발급은 같은 세션을 유지하므로, 갱신 직전의 아직 만료되지 않은 AT도 계속 사용할 수 있다.

여기서 단일 로그인은 **계정당 하나의 로그인 세션**을 의미한다. 동일 브라우저 프로필의
탭은 쿠키를 공유한다. 같은 기기라도 다른 브라우저·프로필에서 로그인하면 이전 세션을 교체한다.
물리적 기기를 식별하거나 복제된 동일 세션 토큰의 동시 사용을 탐지하는 기능은 포함하지 않는다.

다음 범위는 별도로 다룬다.

- 이미 인증 검사를 통과한 요청의 취소, 열린 스트리밍 연결의 강제 종료.
- 기기 목록·세션 이력·사용자 선택에 따른 특정 기기 로그아웃.
- 응답이 유실된 재발급 결과의 재전달과 이전 RT의 재사용 유예.

## 2. 현재 구현과 변경점

아래 표는 변경 전과 Auth 구현 후의 차이다. BFF 행은 후속 구현 계약이며 운영 반영 상태를 뜻하지 않는다.

| 항목 | 변경 전 | 변경 후 계약 |
|---|---|---|
| 저장 단위 | `auth:refresh:{jti}`에 사용자 UUID 저장 | `auth:session:{userId}`에 세션과 현재 RT 저장 |
| 로그인 | 기존 RT를 유지하고 새 RT 추가 | 사용자 레코드를 새 세션으로 교체 |
| AT·RT 연결 | 각각의 `jti`만 있고 공통 세션 ID 없음 | 두 토큰에 같은 `sid` 포함 |
| 재발급 | 기존 RT `GETDEL` 후 새 RT 별도 저장 | 세션·RT 일치 확인과 교체를 원자적으로 수행 |
| 로그아웃 | 입력 RT의 `jti` 키 삭제 | 입력 RT의 세션이 현재 세션일 때만 삭제 |
| BFF 보호 API | 기존 설계는 AT 자체 검증만 수행 | AT 검증 후 Redis에서 활성 세션 확인 |

변경 후 Auth 구현은 [LoginService](../../src/main/java/com/loresentry/authentication/application/service/LoginService.java),
[RefreshService](../../src/main/java/com/loresentry/authentication/application/service/RefreshService.java),
[RevokeService](../../src/main/java/com/loresentry/authentication/application/service/RevokeService.java),
[RedisSessionStore](../../src/main/java/com/loresentry/authentication/adapter/out/redis/RedisSessionStore.java),
[RsaJwtTokens](../../src/main/java/com/loresentry/authentication/adapter/out/jwt/RsaJwtTokens.java)다.
현재 [BFF AuthController](../../../loresentry-gateway/src/main/java/com/loresentry/gateway/web/AuthController.java)는
연결 확인용 `GET /auth`만 제공한다. BFF 인증 흐름은 기존 설계 구현과 함께 반영해야 한다.

## 3. 책임과 데이터 계약

| 구성 요소 | 책임 |
|---|---|
| Auth | 신원 검증, 세션 ID 생성, AT·RT 발급, Redis 상태 생성·교체·삭제 |
| BFF | 브라우저 보안, AT 검증, 활성 세션 조회, 검증된 사용자 정보 전달 |
| Redis/Valkey | 사용자별 현재 세션과 RT의 공유 상태 보관, 조건부 변경의 원자적 실행 |
| 프론트 | 명시적 재발급과 탭 간 조율, 인증 오류에 따른 재로그인 안내 |

BFF는 자체 `HttpSession`이나 사용자별 메모리 상태를 만들지 않는다.
다만 인증 판단은 공유 Redis 상태에 의존하므로, 기존의 저장소 조회 없는 JWT 인증 계약은 변경된다.
Auth 저장소에 대한 BFF의 세션 조회를 명시적인 서비스 간 계약으로 허용한다.
Auth 내부 저장 구조를 임의로 읽는 범위를 다른 서비스·키로 확대하지 않는다.

### Redis 레코드

Redis String에 JSON을 저장한다. 키의 `{userId}` 표기는 실제 사용자 UUID로 치환한다.
사용자 ID는 키로 표현하며 값에 중복 저장하지 않는다.

```text
키: auth:session:0195a860-0000-7000-8000-000000000001
```

```json
{
  "schema_version": 1,
  "sid": "8ab8809c-ff40-48c3-9010-bbf4a609017c",
  "refresh_jti": "4a51f5d7-2d47-42e7-9d70-4c55ea336f8a",
  "refresh_expires_at": 1791417600
}
```

| 필드 | 계약 |
|---|---|
| `schema_version` | 정수 `1`. 지원하지 않는 버전은 저장소 계약 오류로 처리 |
| `sid` | 로그인 시 생성하는 UUID v4. 재발급 동안 유지하고 재로그인 시 교체 |
| `refresh_jti` | 현재 RT의 `jti`. 재발급마다 새 UUID v4로 교체 |
| `refresh_expires_at` | 현재 RT의 `exp`와 같은 UTC Unix 초 정수 |

AT·RT 원문과 개인정보는 값에 저장하지 않는다. Redis 키에는 내부 사용자 ID가 포함되므로
로그·진단 출력에서도 식별자 노출을 최소화한다.

키 만료는 `refresh_expires_at`과 맞춘 절대 만료 시각으로 지정한다.
값과 만료 시각은 `SET ... PXAT <exp × 1000>` 한 번으로 설정하며, 별도 `EXPIRE`로 나누지 않는다.
이 명령은 값 교체와 절대 만료 지정을 지원한다. [Redis SET 문서](https://redis.io/docs/latest/commands/set/)

기존 수명 정책인 AT 15분·RT 14일을 유지한다. 갱신 성공 시 RT는 새 발급 시각부터
14일로 연장하고, 최초 로그인 기준 최대 유지 기간은 추가하지 않는다.
BFF의 일반 조회는 만료를 연장하지 않는다. JWT의 30초 시계 오차 허용과 별개로
저장소 만료에는 유예를 더하지 않으며, 세션이 만료되면 AT가 시간 검증을 통과해도 거절한다.

### JWT와 HTTP 계약

[기존 JWT 필드](JWT_DESIGN.md#jwt-필드와-검증)에 UUID v4 문자열 `sid`를 필수로 추가한다.
`sub`, `iss`, `aud`, `iat`, `exp`, `jti`, `token_type`, JOSE 헤더와 검증 규칙은 유지한다.
AT와 RT의 `jti`는 서로 다르고, `sid`는 같다.

로그인·재발급의 내부 응답은 기존 네 필드인 `access_token`, `access_expires_at`,
`refresh_token`, `refresh_expires_at`을 유지한다. `sid`는 서명된 토큰 안에 담으며
브라우저용 JSON이나 별도 쿠키로 전달하지 않는다. Redis의 시각 표현과 달리
HTTP의 만료 시각은 기존 UTC ISO 8601 문자열을 유지한다.

## 4. 로그인과 요청 인증

### 로그인: 새 세션으로 교체

1. Auth가 기존 OAuth 흐름에 따라 신원을 검증하고 계정 DB 트랜잭션을 커밋한다.
2. 새 `sid`를 생성하고 같은 `sid`를 가진 AT·RT를 서명한다.
3. 사용자 키를 새 레코드와 만료 시각으로 덮어쓴다. 기존 키를 먼저 삭제하지 않는다.
4. 저장 성공이 확인되면 토큰 쌍을 BFF에 반환한다. BFF는 기존 쿠키 계약대로 전달한다.

동시 로그인은 **Redis에서 마지막으로 적용된 세션 교체가 유효하다.**
로그인 시작 시각이나 HTTP 응답 도착 순서를 기준으로 하지 않는다.
따라서 성공 응답을 받은 토큰이라도 다른 로그인이 뒤이어 적용되면 이미 무효일 수 있다.
프론트는 기존대로 로그인 성공 후 `/auth/users/me`로 상태를 확인한다.

서명 실패 등 저장 명령 전 실패는 이전 세션을 바꾸지 않는다. 저장 타임아웃이나 응답 유실은
새 세션으로 교체됐을 가능성이 있으므로 이전 세션 유지도, 새 로그인 성공도 보장하지 않는다.
저장 실패·결과 불명에서는 토큰을 반환하지 않고 `LOGIN_UNAVAILABLE`을 반환하며 로그인 흐름을 다시 시작한다.
DB 계정은 유지하고, 이전 세션 복구나 결과 불명인 저장 명령의 자동 재전송은 하지 않는다.

### 보호 API: AT 검증 후 세션 확인

1. BFF가 기존 계약에 따라 상태 변경 요청의 CSRF를 검사한다.
2. AT의 서명·헤더·필수 클레임·시각을 검증한다. `sid` 누락·형식 오류도 거절한다.
3. 검증된 `sub`로 키를 만들고 Redis의 쓰기 담당 노드에서 `GET`한다.
4. 레코드 형식·만료와 `sid` 일치를 확인한다.
5. 통과한 요청만 내부 서비스로 전달하며, 사용자 헤더는 검증된 `sub`에서 만든다.

요청에서 전달받은 사용자 헤더나 검증 전 JWT 값으로 조회하지 않는다.
요청마다 한 번 조회하고 로컬 허용 캐시·읽기 복제본은 사용하지 않는다.
이는 캐시·복제 지연 동안 이전 세션을 허용하는 일을 피하기 위한 선택이다.
BFF는 RT 쿠키의 존재나 `refresh_jti` 일치를 일반 API의 인증 조건으로 사용하지 않는다.

로그인·콜백은 일반 AT 검사를 요구하지 않는다. 재발급·로그아웃은 CSRF 후 Auth에 RT를
전달하며, 상태 판단과 변경은 Auth가 수행한다. BFF가 이를 일반 보호 API 필터로 막지 않는다.

새 로그인·로그아웃의 차단 효과는 변경 이후 Redis를 조회하는 요청부터 적용된다.
이미 조회를 통과한 요청에는 소급하지 않는다.

## 5. 재발급: 같은 세션 안에서 RT 교체

1. Auth가 RT의 서명·필수 클레임·만료를 검증한다.
2. 입력 RT의 `sid`를 유지하고 새 AT·RT를 미리 서명한다. 아직 응답으로 반환하지 않는다.
3. Redis에서 아래 조건 확인과 새 레코드 저장을 하나의 Lua 스크립트로 수행한다.
4. 교체 성공이 확인된 요청에만 새 토큰 쌍을 반환한다.

| 원자적 처리 단계 | 조건·동작 |
|---|---|
| 현재 상태 확인 | 키가 있고 레코드 형식이 유효하며 아직 만료되지 않았는지 확인 |
| 입력 대조 | 저장된 `sid`, `refresh_jti`, 만료 시각이 검증된 RT의 `sid`, `jti`, `exp`와 일치 |
| 새 값 검증 | 같은 `sid`, 새 RT 식별자, 미래 만료 시각인지 확인 |
| 교체 | JSON과 새 절대 만료 시각을 최종 `SET ... PXAT` 한 번으로 기록 |

시각 비교는 스크립트 안에서 Redis 서버 시각을 기준으로 수행한다.
조건 불일치·부재·만료는 쓰기 없이 거절한다. 파싱·인자 검사를 모두 쓰기 전에 끝내고,
최종 쓰기 뒤에는 실패 가능한 추가 저장 명령을 두지 않는다.
Lua의 원자적 실행은 다른 명령의 중간 개입을 막지만 DB 트랜잭션의 오류 롤백과 같지는 않다.
[Redis Lua 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)

기존 `GETDEL`과 별도 저장을 제거하므로 정상 갱신 중 세션 키가 일시적으로 사라지지 않는다.
같은 RT로 동시에 갱신하면 최대 한 요청만 교체에 성공한다. 실패한 요청이
현재 세션을 삭제하거나 새 RT를 덮어쓰지 않는다.

응답 유실이나 실행 결과 미확인은 자동 재시도·복구하지 않는다.
이전 RT가 이미 교체됐다면 재사용 요청은 거절한다. RT 불일치만으로 현재 세션 전체를
폐기하지 않으며, 재사용 공격 탐지를 위한 별도 토큰 이력은 이 설계에 포함하지 않는다.
[기존 탭 간 조율](../../../docs/frontend/TOKEN_REFRESH.md)은 계속 필요하다.

## 6. 로그아웃: 현재 세션 조건부 삭제

Auth는 전달받은 RT의 서명·발급자·대상·토큰 종류·필수 클레임을 검증한다.
유효한 미만료 RT라면 사용자 키를 조회하고 `sid`가 일치할 때만 삭제하는 Lua 스크립트를 실행한다.
키가 없거나 다른 `sid`이면 삭제하지 않고 `204`로 완료한다. 다른 세션의 토큰이기 때문이다.

**로그아웃에서는 현재 `refresh_jti` 일치를 요구하지 않는다.**
같은 세션에서 갱신과 로그아웃이 겹쳐 RT가 먼저 교체돼도 세션을 종료하기 위한 선택이다.
이에 따라 이미 회전된 RT도 서명과 세션이 유효하고 그 RT 자체가 만료 전이라면
해당 세션을 로그아웃할 수 있다. 새로운 로그인은 다른 `sid`를 사용하므로 삭제되지 않는다.

서명·필수 필드는 유효하지만 만료된 RT는 기존처럼 변경 없이 `204`로 처리한다.
따라서 이 응답은 입력 RT가 더 이상 사용될 수 없다는 뜻이며,
같은 계정의 모든 세션이 없어졌다는 보증은 아니다. 만료 RT의 `sid`가 같다는 이유로
그동안 갱신된 활성 세션을 삭제하지 않는다.

조건부 삭제는 기존의 제한된 재시도 예산을 유지한다. 최초 포함 최대 3회,
재시도 전 100ms·200ms 대기, 명령별 최대 500ms, 전체 최대 2초다.
각 시도는 동일한 `sid` 조건을 유지한다. 타임아웃 후 새 로그인이 생겨도 지우지 않는다.
스크립트에서도 입력 RT의 `exp`를 Redis 서버 시각과 비교한다.
대기·재시도 중 RT가 만료됐다면 삭제하지 않고 완료한다.

BFF는 기존대로 CSRF를 통과한 로그아웃에서 폐기 성공 여부와 관계없이 쿠키 삭제 헤더를 반환한다.
외부 `refresh_revocation` 필드는 호환성을 위해 유지하고 입력 RT에 대한 폐기 결과로 해석한다.
RT가 없으면 Auth를 호출하지 않고 `not_requested`를 반환한다.
브라우저 쿠키 삭제만으로 서버 세션 삭제가 보장되지는 않는다.

## 7. 동시성 보장

| 경쟁 상황 | 기대 결과 |
|---|---|
| 로그인 A와 로그인 B | Redis에 마지막으로 저장된 `sid` 하나만 활성 |
| 같은 RT로 두 번 갱신 | 한 번만 성공. 두 번째 요청은 RT 식별자 불일치로 거절 |
| 이전 세션 갱신과 새 로그인 | 갱신이 먼저면 새 로그인이 교체. 로그인이 먼저면 이전 세션 갱신 거절 |
| 이전 세션 로그아웃과 새 로그인 | 이전 세션의 삭제가 새 `sid`를 지우지 않음 |
| 같은 세션 갱신과 로그아웃 | 갱신이 먼저면 그 세션 삭제. 삭제가 먼저면 갱신이 부재로 실패 |
| BFF 조회와 RT 갱신 | `sid`가 같고 키 부재 구간이 없어 미만료 AT의 접근 유지 |

삭제한 세션을 재발급이 다시 생성해서는 안 된다. 재발급 스크립트는 키가 없으면 실패하며,
세션을 새로 생성할 수 있는 흐름은 로그인뿐이다.
Auth·BFF 인스턴스가 여러 개여도 모든 인스턴스가 같은 저장소를 사용하고 동일한 조건을 적용한다.
프로세스 내부 잠금만으로 이 규칙을 구현하지 않는다.

## 8. 오류와 장애 처리

### BFF 보호 API

기존 AT 오류에 아래 두 코드를 추가한다. 실패 요청은 내부 서비스에 전달하지 않는다.

| HTTP | code | 조건 | next_action |
|---|---|---|---|
| 401 | `ACCESS_TOKEN_MISSING` | AT 부재 | `REFRESH` |
| 401 | `ACCESS_TOKEN_EXPIRED` | 만료 외 검증은 통과한 AT의 만료 | `REFRESH` |
| 401 | `ACCESS_TOKEN_INVALID` | 서명·필수 클레임 검증 실패. `sid` 누락·형식 오류 포함 | `RELOGIN` |
| 401 | `SESSION_INVALID` | 세션 부재·만료 또는 `sid` 불일치 | `RELOGIN` |
| 503 | `SESSION_UNAVAILABLE` | 연결·시간 초과·ACL 오류, 잘못된 레코드·미지원 버전 등 검증 불가 | `RETRY_LATER` |

AT 부재·만료는 기존처럼 재발급 시도를 허용하며, Auth가 그 시점에 세션을 검사한다.
`SESSION_INVALID`에서는 자동 재발급을 하지 않는다. 이 오류만으로 다른 기기 로그인,
로그아웃, 만료, 저장소 상태 유실을 구분할 수 없으므로 특정 원인으로 단정해 안내하지 않는다.

세션 검사 실패 응답은 AT·RT 쿠키를 설정·삭제하지 않는다. 이전 요청의 늦은 오류가
새 로그인 쿠키를 지우지 않도록 하기 위한 선택이다. 프론트는 실패한 요청을 중단하고,
기존 로그인·재발급 완료와 오류 응답의 순서를 고려해 결과를 처리한다.

조회 장애는 인증 성공으로 통과시키거나 로그아웃으로 단정하지 않는다.
초기 BFF 조회 시간 제한은 연결 획득을 포함해 500ms로 두고 요청 내 자동 재시도를 하지 않는다.
이는 구현 초깃값이며 연동 시 지연 측정과 상위 요청 시간 예산으로 검증한다.

### Auth 상태 변경

| 상황 | 처리 |
|---|---|
| 로그인 저장 실패·결과 불명 | `503 LOGIN_UNAVAILABLE`, `RESTART_LOGIN`. 새 토큰 미반환 |
| RT 검증 실패 또는 갱신 조건 불일치 | `401 REFRESH_REJECTED`, `RELOGIN`. 현재 상태 유지 |
| 갱신 저장소 명령 미실행 확인 | `503 REFRESH_UNAVAILABLE`, `RETRY_LATER` |
| 갱신 실행 결과 미확인 | `503 REFRESH_OUTCOME_UNKNOWN`, `RELOGIN` |
| 폐기 입력의 RT 검증 실패 | `401 INVALID_REFRESH_TOKEN`, `NONE` |
| 조건부 폐기 완료 미확인 | `503 REVOCATION_UNCONFIRMED`, `NONE` |
| 조건부 변경 전 발견한 잘못된 저장 레코드 | `500 INTERNAL_ERROR`, `NONE`. 상태 변경 없이 진단 |
| 그 밖의 미분류 내부 결함 | `500 INTERNAL_ERROR`, `NONE`. 상태 변경 여부를 임의로 단정하지 않음 |

새 토큰 서명 실패는 Redis 변경 전에 발생한다. 기존 세션은 유지하며
`500 INTERNAL_ERROR`로 처리한다. 소비 후 별도 저장 단계가 없어지므로
새 갱신 경로는 기존 `REFRESH_SAVE_FAILED`를 발생시키지 않는다.

실행 여부는 연결·타임아웃 예외 이름만으로 단정하지 않는다. 결과 불명인 변경을
자동 재전송하지 않으며, 조건부 폐기에만 앞 절의 제한된 재시도를 적용한다.
`NOSCRIPT`처럼 스크립트 본문 미실행이 확인된 경우의 재로딩은 이와 구분한다.

Redis 상태가 유실되면 해당 사용자는 재로그인해야 한다. 요청별 조회와 스크립트의 원자성은
페일오버 중 승인된 쓰기의 영속성까지 보장하지 않는다. 오래된 스냅샷 복구 등으로 폐기 전
상태가 되살아날 가능성은 배포 저장소 설정과 복구 절차에서 검증한다.
불확실한 과거 세션 상태를 그대로 서비스에 재사용하지 않는 복구 절차가 필요하다.

## 9. Redis 권한과 운영 경계

Auth와 BFF는 별도 자격 증명을 사용한다.

| 계정 | 허용 범위 |
|---|---|
| BFF | `auth:session:*`에 대한 `GET`과 검증된 연결 초기화·상태 확인 명령만 허용 |
| Auth | 세션 키의 조회·저장·조건부 삭제 스크립트 실행과 필요한 명령 허용. OAuth 상태 권한은 기존대로 유지 |

BFF에는 `SET`, `DEL`, `GETDEL`, `EVAL`, `EVALSHA`, 키 탐색·관리 명령과
`auth:refresh:*`, OAuth 임시 상태에 대한 접근을 허용하지 않는다.
`+@read` 전체를 주는 대신 필요한 명령과 키 패턴을 제한한다.
Redis ACL은 명령과 키 패턴별 권한 제어를 지원한다. [Redis ACL 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

String 레코드를 한 번에 읽으므로 BFF는 현재 RT 식별자·만료 정보도 읽게 된다.
이는 RT 원문이나 발급 권한을 주는 것은 아니다. RT 메타데이터까지 숨겨야 한다면
별도 조회 레코드 또는 Auth 조회 API가 필요하며, 현재의 단일 레코드 범위에는 포함하지 않는다.

Auth에는 실제 스크립트와 드라이버가 쓰는 `GET`, `SET`, `DEL`, `TIME`,
스크립트 로딩·실행 명령을 식별해 허용한다. BFF 연결 초기화 명령도 실제 클라이언트로 확인한다.
운영의 Redis 호환 Valkey 버전에서 명령·ACL·Lua 동작을 검증하고,
BFF의 신규 연결 경로에 맞춰 네트워크 접근과 자격 증명 주입을 설정한다.

조회 지연·오류, 세션 불일치, 갱신 경쟁 실패와 결과 미확인을 관측한다.
토큰 원문을 기록하지 않으며 사용자 ID·`sid`를 메트릭 라벨로 사용하지 않는다.

## 10. 구현 대상과 전환

### 구현 대상

| 대상 | 변경 내용 |
|---|---|
| Auth JWT 포트·어댑터 | `issue(userId, sid)`로 세션을 입력받고 `RefreshClaims`에 `sid` 추가 |
| Auth 저장 포트 | `RefreshTokenStore`를 `SessionStore`로 교체. 로그인 교체·조건부 갱신·조건부 삭제를 각각 표현 |
| Auth 서비스 | 로그인에서 `sid` 생성, 갱신에서 유지, 폐기에서 세션 조건 적용 |
| Auth Redis 어댑터 | JSON·절대 만료 계약과 Lua 스크립트 구현. 부재·불일치·장애·결과 불명 구분 |
| BFF | AT 인증 흐름에 읽기 전용 세션 조회 추가, 오류·시간 제한·내부 전달 차단 구현 |
| 프론트 | `SESSION_INVALID` 재로그인과 `SESSION_UNAVAILABLE` 일시 장애 처리, 늦은 응답 조율 |
| 인프라 | BFF 전용 ACL·자격 증명·네트워크 연결, 쓰기 담당 노드 조회 설정 |

클래스명은 구현 시 정하되 원자적 연산을 서비스의 별도 `find`·`save` 호출로 분해하지 않는다.
회원 DB와 OAuth 임시 상태 구조는 이 변경으로 수정하지 않는다.

### 기존 세션 전환

기존 AT·RT에는 `sid`가 없으므로 새 구조로 자동 승계하지 않고 재로그인을 요구한다.
기존 `auth:refresh:*` 키를 이용한 fallback과 두 저장 방식의 동시 인증은 제공하지 않는다.
기존 키는 TTL로 정리하며 전환을 위해 Redis 전체를 삭제하지 않는다.

1. Auth·BFF·프론트 변경과 ACL·접속 설정을 준비하고 연동 테스트를 완료한다.
2. 전환 중 인증 관련 트래픽과 보호 API를 제어하고, 진행 중인 이전 요청을 배출한다.
3. 모든 Auth·BFF 인스턴스를 새 계약으로 전환하고 기존 인스턴스를 제거한다.
4. `sid` 없는 토큰 거절, 새 로그인, 세션 교체·갱신·로그아웃과 오류 처리를 확인한다.
5. 트래픽을 재개한다. 이 절차는 기존 로그인 유지나 무중단 전환을 보장하지 않는다.

Auth만 또는 BFF만 바꾸면 이전 토큰을 발급하거나 세션 검사 없이 허용하는 경로가 생긴다.
혼재 배포 상태를 전환 완료로 판단하지 않는다.
롤백도 Auth·BFF 계약을 함께 맞춰야 하며, 구버전 복귀 시 남아 있는 이전 RT 키와
같은 서명키로 기존 로그인이 다시 허용될 수 있다. 트래픽을 제어한 상태에서
이전 키의 범위 제한 폐기 또는 서명키 교체 등 재인증 방안을 확정한 뒤 실행한다.

## 11. 완료 기준과 검증 시나리오

아래는 구현 후 수행할 검증 계획이며, 이 문서 작성 중 실행한 테스트가 아니다.
Auth 어댑터 통합 테스트와 BFF·브라우저 연동 테스트로 나누어 확인한다.

| 시나리오 | 검증할 결과 |
|---|---|
| 첫 로그인 | 사용자 레코드 하나, AT·RT의 동일 `sid`, RT `jti`·만료와 저장값 일치 |
| 다른 기기 로그인 | 이전 AT는 만료 전에도 BFF에서 거절, 이전 RT도 갱신 거절, 새 기기는 통과 |
| 정상 갱신 | `sid` 유지, RT `jti`·만료 교체, 이전 RT 재사용 거절, 이전 미만료 AT는 통과 |
| 동시 갱신 | 독립 Auth 인스턴스의 동일 RT 요청 중 최대 하나만 성공, 실패가 성공 상태를 삭제하지 않음 |
| 로그인·갱신 경쟁 | 두 실행 순서에서 새 세션을 이전 세션 갱신이 덮어쓰지 않음 |
| 로그인·로그아웃 경쟁 | 이전 `sid`의 삭제·재시도가 새 세션을 삭제하지 않음 |
| 갱신·로그아웃 경쟁 | 두 실행 순서에서 세션 종료, 재발급으로 삭제된 세션 부활 불가 |
| 폐기 입력 경계 | 회전된 미만료 RT는 같은 세션 삭제 가능, 만료 RT는 변경 없이 완료, 잘못된 서명은 거절 |
| 만료·부재 | TTL 만료 또는 상태 유실 시 AT 시간 검증과 별개로 세션 거절, 조회로 TTL 연장 없음 |
| 응답·명령 결과 유실 | 로그인·갱신의 결과 불명을 성공으로 처리하거나 자동 재전송하지 않음 |
| Redis 장애·레코드 손상 | BFF는 503으로 차단하고 내부 호출·쿠키 삭제를 하지 않음 |
| BFF 다중 인스턴스 | 어느 BFF로 요청해도 교체 후 이전 세션 거절, 허용 캐시·복제본 지연 없음 |
| ACL | BFF의 세션 읽기 성공, 쓰기·스크립트·다른 키 조회 거절, 실제 드라이버 연결 성공 |
| 기존 토큰 전환 | `sid` 없는 AT·RT 거절, 구 저장 키 fallback 없음 |
| 브라우저 연동 | 세션 오류로 재발급 반복 없음, 실패 응답이 새 쿠키를 지우지 않음, RT 없는 로그아웃 결과 구분 |
