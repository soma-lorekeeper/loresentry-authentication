# 단일 세션 ID 로그인 설계

**브라우저 인증에는 난수 세션 ID 하나를 사용한다. 사용자마다 활성 로그인은 하나이며,
마지막 인증 활동으로부터 14일 동안 유지하고 활동할 때마다 만료를 연장한다.**

- 기준일: 2026-09-26. 단일 ID와 활동 시 연장은 사용자 결정이다.
- 상태: Auth·BFF 코드와 설정에 반영했다. 구현 검증 기록은 각 저장소의 580–589 이슈 문서를 따른다. 브라우저·운영 전환 검증은 후속 작업이다.
- 원본 범위: Auth·BFF의 세션 형식, 저장 구조, 인증·연장·폐기와 동시성 계약.
- 내부·외부 HTTP 계약은 [Auth API](../INTERNAL_API.md),
  [BFF API](../../../loresentry-gateway/docs/EXTERNAL_API.md)를 따른다.

## 책임과 적용 범위

| 구성 요소 | 책임 |
|---|---|
| Auth | Google 신원 검증, 계정 관리, 세션 생성·교체·조건부 폐기 |
| BFF | 쿠키·CSRF·CORS, 공유 세션 검증과 활동 만료 연장, 검증된 사용자 전달 |
| Redis/Valkey | 공유 세션과 사용자별 활성 세션 인덱스, 원자적 상태 변경 |
| 프론트 | 쿠키 포함 요청, 로그인 확인·로그아웃·재로그인, 인증 전환과 진행 요청 조율 |

BFF 인스턴스는 사용자별 로컬 상태나 별도 HttpSession을 만들지 않는다.
인증 상태의 원본은 공유 저장소다. 세션 생성·교체·폐기는 Auth만 수행하며,
BFF에는 기존 세션의 검증과 TTL 연장을 명시적으로 허용한다.

단일 로그인은 계정당 활성 세션 하나를 의미한다. 같은 브라우저 프로필의 탭은 쿠키를
공유하고 다른 브라우저·프로필의 새 로그인은 기존 세션을 교체한다. 물리적 기기 식별,
복사된 동일 인증값의 동시 사용 탐지, 이미 인증한 요청 취소와 열린 스트림 종료는 포함하지 않는다.

## 세션 ID

Auth는 로그인마다 CSPRNG로 독립적인 32바이트를 생성하고 padding 없는 Base64URL로
인코딩한다. `session_id`는 43자의 정규 표현이며 사용자 ID·시각·권한을 포함하지 않는다.
길이·문자 집합과 디코딩 후 재인코딩 일치를 검사한다. 사용자 UUID나 기존 식별자를
인증 비밀값으로 재사용하지 않는다. 저장 전 충돌이 확인되면 새로운 값을 생성한다.

원문은 로그인 내부 응답과 BFF의 HttpOnly 쿠키에만 전달한다. 브라우저 JSON·URL·로그·
메트릭에는 넣지 않는다. Redis에는 `SHA-256(ASCII(session_id))`의 소문자 64자리 hex만
저장한다. 해시를 클라이언트 인증값으로 받지 않는다. 해시를 알아도 원문 없이 인증할 수 없어야 한다.
Google 신원 확인의 OIDC 검증과 임시 로그인 상태는 별도 흐름으로 유지한다.

## 수명과 활동

비활동 제한은 정확히 1,209,600초다. 로그인과 각 보호 요청의 인증 성공 시 Redis 서버
시각에 14일을 더해 만료를 설정한다. 최초 로그인 기준의 별도 절대 수명 상한은 두지 않는다.

활동은 **CSRF 등 선행 검사를 통과하고 활성 세션 검증에 성공한 보호 API 요청**이다.
그 뒤 도메인 처리가 오류로 끝나도 이미 성공한 인증 활동은 유지한다. 공개 헬스 체크,
CORS 사전 요청, 로그인 준비·콜백 실패, 인증 실패와 로그아웃은 기존 세션을 연장하지 않는다.
열린 화면의 마우스 움직임이나 진행 중인 스트림만으로는 연장되지 않는다. 로그인 유지만을
목적으로 한 주기적 요청은 추가하지 않는다. 보호 API의 자동 폴링은 활동으로 계산되므로
폴링이 계속되면 세션도 계속 유지된다.

쿠키 수명도 [BFF 쿠키 계약](../../../loresentry-gateway/docs/BROWSER_SECURITY.md#세션-쿠키)에
따라 같은 만료 시각까지 연장한다. 서버 TTL만 늘리고 쿠키를 최초 발급 시각에 고정하지 않는다.
연장은 ID 교체가 아니다. 같은 세션에서는 ID를 유지하고 새 로그인 때 새 ID를 발급한다.

별도 절대 상한을 두지 않으므로 탈취된 ID도 활동을 지속하면 유지될 수 있다.
이것은 선택한 정책의 한계이며 자동 연장이 탈취 방어를 대신하지 않는다.
추후 민감 작업·권한 변경을 도입하면 재인증과 ID 교체 정책을 함께 설계한다.
[OWASP는 비활동 만료와 별개로 절대 만료도 권고한다.](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#absolute-timeout)

## Redis 레코드

난수 ID로 사용자를 찾는 인덱스와 사용자별 현재 세션을 나눈다. 둘 다 Redis String의
UTF-8 JSON이다. 원문 인증값과 이메일·표시 이름은 저장하지 않는다.

| 키 | 값 |
|---|---|
| `auth:session:{login}:by-id:<session_hash>` | `schema_version: 2`, `user_id: UUID`, `created_at: UTC epoch 초 정수` |
| `auth:session:{login}:by-user:<user_id>` | `schema_version: 2`, `session_hash: 소문자 SHA-256 hex` |

`<...>`만 치환하고 `{login}`은 실제 키에 남는 고정 Redis hash tag다. 두 키를 같은 슬롯에
두어 스크립트의 다중 키 변경을 지원한다. 초기 단일 쓰기 노드를 전제로 하며, 클러스터에서도
세션 전체가 한 슬롯에 모인다. 세션을 여러 샤드로 분산하려면 키·원자성 계약을 재설계한다.

만료의 원본은 두 키의 Redis TTL이다. JSON에 갱신해야 할 만료 필드를 중복 저장하지 않는다.
두 키는 같은 절대 밀리초 시각에 만료시킨다. API의 `expires_at`은 해당 연산이 적용한 만료
시각을 UTC ISO 8601로 변환한 값이다. TTL이 없는 키는 손상으로 취급하며 인증하지 않는다.
스키마·필수 필드·UUID·해시·시각 범위를 검증하고 중복·알 수 없는 JSON 필드를 거절한다.

## 로그인

1. OAuth 검증과 계정 DB 커밋을 마친 뒤 새 세션 ID와 해시를 만든다.
2. Lua에서 새 by-id 키의 부재, 기존 by-user 값·TTL의 유효성과 입력을 확인한다.
3. 새 by-id 레코드를 생성하고 by-user를 새 해시로 교체한다. 두 키에 같은 14일 만료를 설정한다.
4. 저장 성공을 확인한 경우에만 `session_id`, `expires_at`을 BFF에 반환한다.

이전 by-id 레코드는 남은 TTL로 정리한다. by-user가 더 이상 가리키지 않으므로 인증과
연장에 사용할 수 없다. 로그인 횟수에 따른 잔여 인덱스 메모리를 운영에서 측정한다.
새 로그인에서 기존 키를 먼저 삭제하지 않는다. 동시 로그인은 Redis에 마지막으로 적용된
교체 하나만 활성이다. 응답 도착 순서와 다를 수 있어 프론트는 로그인 후 본인 계정을 조회한다.

저장 실패·결과 미확인은 `LOGIN_UNAVAILABLE`이며 ID를 반환하지 않는다. 계정 DB는
유지하고 로그인 교체를 자동 재전송하거나 이전 상태를 복원하지 않는다. 생성 단계 실패는
저장 전이라면 기존 세션에 영향을 주지 않는다. 저장 결과 불명에서는 이전 세션 유지도 보장하지 않는다.

## 보호 요청의 검증과 연장

1. BFF가 상태 변경 요청의 CSRF를 검사하고 단일 세션 쿠키의 형식을 검증한다.
2. ID를 해시하고 by-id를 GET해 사용자 UUID를 얻는다. 이 값은 아직 인증된 사용자로 사용하지 않는다.
3. 해당 by-id와 by-user를 명시적인 `KEYS`로 전달해 Lua를 실행한다. 스크립트에서 두 값을
   다시 읽고 형식·사용자 일치·현재 해시 일치·양쪽의 양수 TTL을 모두 검사한다.
4. 통과할 때만 두 키의 TTL을 Redis `TIME + 14일`로 함께 연장하고 사용자 UUID·만료 시각을 반환한다.
5. 성공 결과를 확인한 BFF만 내부 `X-User-Id`를 설정하고 도메인 서비스를 호출한다.
   응답에는 같은 세션 ID의 쿠키 수명 갱신을 적용한다.

첫 조회만으로 인증하거나, 검증과 연장을 독립 명령으로 분리하지 않는다. 로그인·폐기가
첫 조회와 스크립트 사이에 발생해도 마지막 원자적 검사에서 거절되어야 한다.
초기 계약은 요청당 사전 GET 1회와 검증·연장 스크립트 1회이며, 전체 예산은 연결 획득을
포함해 500ms다. 내부 서비스 호출 시간은 별도다. 쓰기 담당 노드를 사용하고 허용 결과
캐시·읽기 복제본·요청 내 자동 재시도는 사용하지 않는다.

연장에는 `PEXPIREAT`를 사용하고 없는 키를 생성하지 않는다. 실행 결과를 확인하지
못했다면 TTL이 늘었을 수 있어도 인증 성공으로 처리하지 않는다. 쿠키를 변경하지 않고
`503 SESSION_UNAVAILABLE`로 내부 호출을 차단한다. 같은 ID의 다음 독립 요청은 다시 검증할 수 있다.
[Redis 만료 명령](https://redis.io/docs/latest/commands/pexpireat/)

## 로그아웃

Auth는 입력 ID 형식을 검증하고 해시로 by-id를 조회한다. 존재하면 사용자 키와 함께
Lua에서 다시 검증한 후, by-user가 같은 해시일 때만 현재 세션을 삭제한다.
다른 로그인이 활성이라면 새 by-user를 건드리지 않고 입력 ID의 이전 by-id만 삭제할 수 있다.
부재·만료·이미 교체된 세션은 사용 불가 상태로 확인하고 `204`를 반환한다.
해당 ID의 폐기 확인은 계정의 모든 로그인 폐기를 뜻하지 않는다.

유효한 형식의 알려지지 않은 ID도 `204`로 처리한다. 잘못된 형식은
`400 INVALID_SESSION_ID`다. 저장소 장애·손상·결과 불명은 `503 REVOCATION_UNCONFIRMED`다.
조건부 폐기만 최초 포함 최대 3회, 대기 100ms·200ms, 시도당 최대 500ms, 전체 최대 2초로
재시도할 수 있다. 각 시도는 동일 ID 해시를 사용하고 새 로그인 상태는 삭제하지 않는다.

BFF는 CSRF를 통과한 로그아웃에서 폐기 결과와 별개로 쿠키 삭제 헤더를 반환한다.
쿠키 부재 시 Auth를 호출하지 않는다. 실제 브라우저 적용과 서버 폐기 결과를 구분한다.

## 동시성과 저장 실패

| 경쟁 상황 | 보장 |
|---|---|
| 로그인 A·B | 마지막으로 적용된 by-user 하나만 유효 |
| 같은 세션의 동시 활동 | 모두 검증 가능. ID는 유지하고 만료는 후속 활동 기준으로 연장 |
| 이전 세션 활동·새 로그인 | 로그인이 먼저면 이전 활동 거절. 활동이 먼저면 이후 로그인이 교체 |
| 활동·로그아웃 | 폐기가 먼저면 연장 불가. 연장이 먼저면 이어지는 폐기로 종료 |
| 이전 세션 로그아웃·새 로그인 | 이전 ID의 요청·재시도가 새 세션을 삭제하지 않음 |

형식·TTL·인자·키 자료형 검증은 쓰기 전에 끝낸다. Lua는 다른 요청의 중간 개입을
막지만 런타임 오류의 쓰기를 롤백하지 않는다. 다중 쓰기 일부가 실패하면 성공을 반환하지
않고 불일치 상태를 인증에서 거절한다. 런타임·ACL 오류를 포함한 실패 주입으로 이를 검증한다.
[Redis 스크립트 실행 계약](https://redis.io/docs/latest/develop/programmability/eval-intro/)

일관된 만료 검사는 한 스크립트에서 얻은 서버 시각 기준으로 한다. 키의 TTL 차이나
비정상 구조는 손상으로 처리하고, 정상 만료·부재·현재 세션 불일치는 인증 무효로 처리한다.
승인된 쓰기의 페일오버 내구성은 별도 문제다. 과거 스냅샷 복구로 폐기 세션이 부활하지
않도록 [공동 전환](../../../loresentry-gateway/docs/ROLLOUT.md)의 재인증 절차를 따른다.

## 오류와 권한

| BFF 결과 | 조건 | 후속 처리 |
|---|---|---|
| `401 SESSION_REQUIRED / RELOGIN` | 쿠키 없음 | 내부 호출 차단 |
| `401 SESSION_INVALID / RELOGIN` | 쿠키 중복·형식 오류, 세션 부재·만료·현재 세션 불일치 | 내부 호출 차단 |
| `503 SESSION_UNAVAILABLE / RETRY_LATER` | 연결·시간 제한·ACL·손상·연장 결과 불명 | 내부 호출 차단 |

검증 실패에서는 쿠키를 설정·삭제하지 않는다. 오류만으로 다른 기기 로그인·자발적 로그아웃·
만료를 구별하지 않는다. 세션을 되살리는 별도 브라우저 API는 제공하지 않는다.

Auth와 BFF는 별도 Redis 자격 증명을 사용한다. BFF 데이터 명령은 새 세션 키 패턴의
`GET`, `EVAL`, `TIME`, `PTTL`, `PEXPIREAT`로 제한한다. 생성·값 변경·삭제 명령과 OAuth
임시 키 접근은 거절한다. Auth에는 세션 생성·폐기 스크립트와 OAuth 상태 명령을 허용한다.
연결 초기화 명령은 실제 드라이버로 확인한다.

ACL은 명령과 키를 제한할 뿐 특정 스크립트 본문이나 '검증 후 14일'이라는 조건을 강제하지
않는다. BFF 자격 증명이 침해되면 허용 키의 TTL을 임의로 바꿀 수 있다는 경계가 있다.
스크립트 구현·네트워크 접근 제한·자격 증명 보호를 함께 검증한다.
운영 구성은 [BFF 운영 준비](../../../loresentry-gateway/docs/OPERATIONS.md)를 따른다.

## 구현과 검증 경계

코드 변경 없이 설계만 전환했다. 구현할 항목은 세션 ID 생성·해시, 두 인덱스와 원자적
생성·검증/연장·폐기, 단일 쿠키와 API, 새 오류 처리, 브라우저 활동 연장 및 인증 전환이다.
기존 실행 결과는 새 설계의 통과 근거가 아니다.

[Auth 테스트 계획](../implementation/TEST_PLAN.md)과
[프론트 인계](../../../loresentry-gateway/docs/FRONTEND_AUTH_CONTRACT.md)를 기준으로
만료 경계·독립 인스턴스 경쟁·장애·ACL·브라우저 쿠키를 검증한 뒤 공동 배포한다.
